scope — AI Integration

Seven copy-paste stages that add Codex-powered chat and HTML reports to your market-research dashboard.

Generated 2026-08-27 · verified against codex-cli 0.150.1 (logged in via subscription, no API key) · model pinned to gpt-5.6-sol @ xhigh reasoning per invocation.

How to use this

  1. Run the stages in order — each builds directly on the files the previous one created.
  2. For each stage, start a fresh session with your coding agent inside the scope project folder and paste the whole prompt.
  3. Each stage ends with its own commit, so you can review the diff between stages.
  4. Each stage card carries a Test it yourself checklist with the manual checks for that moment — tick them off right in this doc; your ticks are saved in this browser.
  5. Nothing hits your Codex subscription during tests: live calls are opt-in via SCOPE_AI_LIVE_TEST=1 (stage 2 smoke test, stage 6 sample report, stage 7 full pass).
  6. You can also hand your agent several stage prompts in one session — the numbering keeps that unambiguous.

Design decisions baked into the prompts

  • One scope abstraction: every entry point (single video, channel multi-select, cross-channel) is just a list of video IDs — chat and reports are built once and reused everywhere.
  • Codex CLI as the runtime AI: codex exec --json spawned server-side, subscription auth only, model/effort pinned per call — your global Codex config is never modified.
  • Sandboxed: chat runs with a read-only sandbox (transcripts are semi-trusted content); report jobs may write only into their own job directory.
  • Quota-friendly: report jobs run sequentially through an in-process queue; all tests use a mocked Codex spawner.
  • Still loopback-only: the app keeps binding to 127.0.0.1 — with your subscription attached, that rule matters more than ever.
  • Design bar in every UI prompt: stages 3–7 carry explicit design requirements — match the existing scope look (Tailwind + the components/ui primitives), quiet and deliberate rather than flashy.

Transcript materialization

Backend foundation: resolve a set of video IDs into validated scope metadata and write per-job transcript files that Codex will later read. No UI. 

This is stage 1 of 7 of the scope AI integration: transcript materialization for AI analysis. Backend only — no UI in this stage.

Context: scope is a single-user, loopback-only YouTube creator dashboard (Next.js App Router, better-sqlite3, vitest). Schema lives in lib/db/migrations.ts: creators, videos (YouTube video id as TEXT primary key), transcripts (video_id primary key, language, source, plain_text). Transcript text is stored in transcripts.plain_text; helpers in lib/transcripts/.

Build a new lib/ai/ module with:

1. lib/ai/scope.ts — resolveScope(videoIds: string[]): validates each ID against the videos table, joins creator display names, and returns per-video metadata (id, title, creator, publishedAt, hasTranscript, durationSeconds) plus which IDs are unknown or missing transcripts. Pure data, no side effects, fully unit-testable.

2. lib/ai/materialize.ts — materializeTranscripts(videoIds: string[]): creates a job directory under data/ai-jobs/<jobId>/transcripts/ and writes one .txt file per video with a short metadata header (title, creator, URL, published date, language, manual/automatic) followed by the plain transcript text. Also writes a manifest.json (scope metadata + file list) at the job root. Return the job dir path and the manifest. Handle missing transcripts per video by excluding that video and recording the exclusion in the manifest.

3. Keep both behind small interfaces so later stages can mock them in tests.

Verification: vitest unit tests for both modules (follow the existing test/fixture patterns), npm run typecheck, npm test. No DB migration is needed for this stage. When everything passes, commit this stage with a descriptive message.

Test it yourself

Nothing visible in the app yet — this stage is pure backend. You'll exercise it for real in stage 4; for now just confirm the agent's tests cover scope resolution and materialization, including the missing-transcript exclusion path.

Codex adapter

The only code that spawns the codex CLI: pinned model and reasoning effort, JSONL event streaming, session resume, abort handling, and a fully mockable interface. 

This is stage 2 of 7 of the scope AI integration: the Codex adapter — the only code in the app that spawns the codex CLI. No UI yet.

Context: stage 1 added lib/ai/scope.ts (scope resolution) and lib/ai/materialize.ts (writes transcripts to data/ai-jobs/<jobId>/). The machine has codex-cli 0.150.1 authenticated via ~/.codex/auth.json from a ChatGPT subscription — never use or request an API key. Do not read or modify ~/.codex/config.toml or auth.json.

Build lib/ai/codex.ts:

1. runCodex(options) spawns: codex exec --json -m gpt-5.6-sol -c model_reasoning_effort="xhigh" -s <read-only|workspace-write> -C <workDir> - with the prompt piped to stdin. Parse stdout as a JSONL event stream and expose it as a typed async iterable (streaming text deltas where the events provide them, plus the final message).

2. Return (or emit) the session/thread id so later stages can continue conversations with codex exec resume <sessionId>. Also support resumeSessionId as an input option that switches the command to codex exec resume.

3. AbortSignal support that kills the child process cleanly; a sane default timeout; map failures to typed errors (not authenticated, codex binary not found, non-zero exit, quota/usage limit).

4. An injectable spawner interface so every test runs without touching the real CLI or the subscription.

Verification: unit tests with a fake spawner feeding fixture JSONL (happy path, resume, abort, non-zero exit). Then run the single opt-in live smoke test guarded by SCOPE_AI_LIVE_TEST=1 — a tiny read-only prompt in a temp dir — exactly once, and report the raw output. If codex rejects the gpt-5.6-sol slug, print the models codex reports as available and stop for my decision. npm run typecheck and npm test must pass; commit this stage when done.

Test it yourself

  • The agent's report shows the live smoke test ran and returned a real answer from Codex.
  • The output confirms gpt-5.6-sol was accepted at xhigh effort — or the agent stopped and asked you to pick a model instead.
  • No leftover processes: pgrep -af "codex exec" prints nothing after the smoke test.
  • All unit tests passed without the live flag — the only subscription call was the single smoke prompt.

Chat API with persistence

POST /api/ai/chat: creates or resumes Codex sessions over any scope, streams events to the browser as SSE, and persists threads and messages in SQLite. 

This is stage 3 of 7 of the scope AI integration: the chat API with persistence and streaming.

Context: stages 1–2 delivered lib/ai/scope.ts, lib/ai/materialize.ts, and lib/ai/codex.ts (typed JSONL event stream, resume support, injectable spawner, typed errors). Routes live under app/api/, data access under lib/, migrations in lib/db/migrations.ts. This is a loopback-only single-user app with no auth by design — keep it that way.

Build:

1. Migration 002: ai_threads (id, title, codex_session_id, selected video IDs as JSON, created_at) and ai_messages (id, thread_id, role, content, created_at). Follow the existing migrator pattern and naming style.

2. POST app/api/ai/chat/route.ts accepting {videoIds, message, threadId?}. New thread: resolveScope, reject if no selected video has a transcript, materialize transcripts (the job dir doubles as the Codex work dir), seed the conversation with one instruction message that frames Codex as a market-research analyst working from the transcript files in its working directory, then send the user's message. Existing thread: codex exec resume with just the new message — transcripts stay in the Codex session context. Stream Codex events to the client as SSE. Persist user and assistant messages and the codex session id. Read-only sandbox, Node runtime.

3. GET app/api/ai/chat/threads (list with scope summary) and GET app/api/ai/chat/threads/[id] (messages) for history.

4. Route tests using the mocked spawner: SSE shape, persistence, the resume path, and error mapping.

Design bar: emit fine-grained streaming events (a working/thinking indicator plus text deltas), not just a final blob, so the stage 4 UI can feel alive instead of frozen while Codex reasons at xhigh.

Before writing route-handler or streaming code, read the relevant bundled Next.js docs in node_modules/next/dist/docs/ — this Next version has breaking changes (see AGENTS.md). Verification: npm run typecheck, npm test, then a manual curl against the endpoint for a video with a cached transcript. Commit this stage when done.

Test it yourself

Chat UI on the video page

"Ask AI" on any video: a reusable streaming chat panel (components/ai/chat-panel.tsx) with thread history — deliberately scope-agnostic so stage 5 can reuse it. 

This is stage 4 of 7 of the scope AI integration: chat UI on the video page.

Context: stage 3 shipped the chat API (SSE streaming, threads, resume, persistence). The video page is app/channels/[id]/videos/[videoId]/page.tsx; the transcript panel is components/video/transcript-panel.tsx; shared UI primitives are in components/ui (button, card, dialog, toast, separator). Match the existing styling conventions.

Build:

1. An "Ask AI" entry point on the video page that opens a side panel (or collapsible section consistent with the transcript panel).

2. components/ai/chat-panel.tsx — a reusable streaming chat component that takes a scope (a list of video IDs) as a prop: message composer, streaming assistant output rendered as it arrives, an abort button while generating, errors surfaced via the existing toast, and auto-scroll that stops fighting the user when they scroll up.

3. Thread history for this video (from the GET endpoints): list past threads, reopen one to continue it, start a new thread.

4. Keep the panel dumb about where the scope comes from — stage 5 will reuse it for channel and cross-channel selections.

Design bar: this panel is the user-facing face of the whole feature — hold it to the app's standard. scope is built on Tailwind CSS 4 with shadcn-style primitives in components/ui (button, card, toast, separator): reuse them rather than inventing styles, and match the transcript panel's spacing, radii, and muted color treatment. Specifically: a quiet but clearly animated working indicator while Codex reasons before any text arrives; incoming text that appears smoothly rather than in jarring chunks; assistant answers rendered with lightweight markdown (paragraphs, lists, bold — no heavy dependency); a clean composer with an obvious send/stop affordance; and a helpful empty state for the no-threads case. Quiet and deliberate over flashy — no gradients or gimmicks, and hover/focus/disabled/error states all consistent with the rest of the app.

Verification: component tests for the chat panel with a mocked SSE fetch (streaming render, abort, error), npm run typecheck, npm test, and a manual pass on a video with a cached transcript. Commit this stage when done.

Test it yourself — first thing you can click

  • Open a video that has a cached transcript and start "Ask AI" — the panel opens without leaving the page.
  • Send a question and watch the answer arrive — you see streaming activity (status/thinking indicator, then text) rather than a frozen panel while the model reasons at xhigh.
  • Grounding check: ask what products, claims, or numbers are mentioned, and spot-check the answer against the transcript panel.
  • Follow-up check: ask "condense your last answer into one sentence" — it should remember the conversation, proving session resume works.
  • Create a second thread, then reopen the first one from history and continue it — both stay independent.
  • Press stop mid-generation — the stream ends cleanly and you can immediately ask something else.
  • Open a video without a cached transcript — you get a clear message (or the entry point is hidden), never a raw error.

HTML report generation

Background jobs that have Codex write a clean, self-contained HTML summary of any scope into its own sandboxed job dir, with a reports list page and a chat action. 

This is stage 6 of 7 of the scope AI integration: HTML report generation.

Context: stages 1–5 delivered chat over any video scope, the Codex adapter (sandbox modes, resume, injectable spawner), and per-job transcript directories under data/ai-jobs/. Reports are a new feature: a clean standalone HTML summary generated by Codex from a scope's transcripts.

Build:

1. Migration: ai_reports (id, scope video IDs as JSON, status queued|running|done|failed, file_path, error, created_at, completed_at).

2. POST app/api/ai/reports accepting {videoIds, threadId?}: insert a queued job. Jobs run sequentially through a small in-process queue — never in parallel, to protect the Codex plan's rate limits.

3. The job: materialize transcripts, then run codex exec with -s workspace-write and -C set to the job directory, with a report prompt template that instructs Codex to write a single self-contained HTML file into its working directory: inline CSS only, no JavaScript, no external requests, with sections for an executive overview, key themes, notable quotes with video attribution, and actionable takeaways; length proportional to the amount of transcript material. Track status transitions, register the produced file path, and map failures to the error column.

4. Serve finished reports through a route handler that reads from the job dir (the app stays loopback-only). Add a reports list page with status polling, and a "Generate report" action in the chat panel that passes the current thread's scope.

5. Treat transcripts as untrusted input: the report job's write access must be limited to its own job directory.

Design bar (two surfaces): (a) the generated report must read like a designed document, not machine output — the prompt template should ask for a restrained accent color, clear typographic hierarchy, a comfortable reading measure, styled pull-quotes with video attribution, subtle section spacing, and print-friendly page breaks; (b) the reports list page reuses the app's card and badge primitives for status, gets a proper empty state, and the "Generate report" action sits naturally within the chat panel's existing layout.

Verification: unit tests for the queue and the job state machine with the mocked spawner, npm run typecheck, npm test, then one opt-in live report via SCOPE_AI_LIVE_TEST=1 on a small selection — report the resulting HTML path so I can open it. Commit this stage when done.

Test it yourself

  • From a chat thread, hit "Generate report" — status moves queued → running → done on its own (no manual refresh needed).
  • Open the finished report — clean layout, inline CSS only, no JavaScript, no external requests.
  • Self-contained proof: open the report file straight from disk in a browser (the reports page shows where it lives) — it renders identically with no server and no network.
  • Check the content: overview, key themes, notable quotes, takeaways — and quotes attribute the correct video.
  • Start two reports back-to-back — the second stays queued until the first completes (never parallel).
  • Reload the page while one is running — the list still shows the correct status.

Hardening, polish & docs

Final pass: readable failure modes, selection/size guardrails, queue recovery after restarts, a live end-to-end verification, and README documentation. 

This is stage 7 of 7 of the scope AI integration: hardening, polish, and documentation.

Context: stages 1–6 delivered the full AI layer — scope resolution, transcript materialization, the Codex adapter (gpt-5.6-sol, xhigh reasoning), chat with SSE streaming on the video page, channel and cross-channel selection, the reusable chat panel, and sequential background HTML reports.

Do a final hardening pass:

1. Error UX sweep: every failure path (codex not authenticated, codex binary missing, quota/usage limit, timeout, abort, empty scope) surfaces a readable message through the existing toast/error UI — no raw stack traces. Aborted streams must kill the child process and leave thread/job state consistent.

2. Guardrails: cap selections at 25 videos per analysis with a clear message; skip videos without transcripts and say what was skipped; cap total materialized bytes and report the truncation.

3. Concurrency and recovery: chat requests serialize per thread, the report queue stays strictly sequential, and on server boot any job stuck in "running" is marked failed.

4. Live end-to-end verification with the real subscription: a chat on one video, a chat on a multi-creator selection, and one generated report — note roughly how much plan quota the pass consumed.

5. Documentation: add an "AI features" section to README.md (what it does, that it shells out to the local codex CLI under the user's own subscription, the SCOPE_AI_LIVE_TEST flag, and why the loopback-only rule matters more now), plus a short docs/ai-features.md if useful.

Design bar: failure and loading states are designed, not defaulted — reuse the existing toast/alert and pending primitives, avoid layout jumps, and make sure a stream that dies mid-answer leaves the conversation visually coherent (the partial answer clearly marked, with an obvious way to retry).

Verification: npm run typecheck, npm run lint, the full vitest suites including integration and e2e; fix anything that falls out. Commit this stage when done.

Test it yourself — full regression

  • Try to select more than 25 videos — a clear cap message appears, no crash.
  • Ask about something the transcripts never mention — the assistant says it isn't covered instead of inventing an answer.
  • Optional failure drill (fully reversible): quit the app, move ~/.codex/auth.json to auth.json.bak, restart, send a chat — you see a readable "not authenticated" error, not a stack trace. Move the file back and restart.
  • Abort a generation, then run pgrep -af "codex exec" — no orphaned Codex processes.
  • Restart the dev server while a report is running — after boot the stuck job reads failed (not "running" forever) and everything else still works.
  • Non-AI regression: add/remove a creator, refresh a feed, fetch and copy a transcript — all still work, and the full test suites are green.
  • Confirm the app still binds to 127.0.0.1 only.
Keep each stage's commit separate — if a stage goes sideways, it's one git revert away from clean.
